# Karpathyに着想を得たClaude Codeガイドライン

> 新しいプロジェクト [Multica](https://github.com/multica-ai/multica) もぜひご覧ください。再利用可能なスキルでコーディングエージェントを実行・管理するためのオープンソースプラットフォームです。
>
> Xでフォロー: [https://x.com/jiayuan_jy](https://x.com/jiayuan_jy)

Claude Codeの挙動を改善するための単一の `CLAUDE.md` ファイルです。LLMによるコーディングの落とし穴についての [Andrej Karpathyの観察](https://x.com/karpathy/status/2015883857489522876) をもとにしています。

[English](./README.md) | 日本語 | [简体中文](./README.zh.md)

## 問題

Andrejの投稿より:

> 「モデルはあなたに代わって間違った仮定を置き、それを確認せずにそのまま突き進みます。混乱を管理せず、確認を求めず、不整合を表面化せず、トレードオフを提示せず、本来押し返すべき場面でも押し返しません。」

> 「モデルはコードやAPIを過度に複雑にし、抽象化を膨らませ、不要になったコードを片付けない傾向が本当に強いです。100行で済むところに、1000行を超える肥大化した構造を実装してしまいます。」

> 「タスクと直交している場合であっても、十分に理解していないコメントやコードを副作用として変更・削除してしまうことが、今でも時々あります。」

## 解決策

これらの問題に直接対応する4つの原則を、1つのファイルにまとめています。

| 原則 | 対応する問題 |
|------|--------------|
| **コードを書く前に考える** | 間違った仮定、隠れた混乱、欠落したトレードオフ |
| **シンプルさを最優先する** | 過度な複雑化、肥大化した抽象化 |
| **外科的に変更する** | 直交する編集、触るべきでないコードへの変更 |
| **ゴール駆動で実行する** | テストファーストによる効果、検証可能な成功条件 |

## 4つの原則の詳細

### 1. コードを書く前に考える

**仮定しない。混乱を隠さない。トレードオフを表面化する。**

LLMはしばしば、解釈を黙って1つ選び、そのまま進めてしまいます。この原則は、明示的な推論を強制します。

- **仮定を明示する** — 不確かな場合は、推測せずに質問する
- **複数の解釈を提示する** — 曖昧さがあるときに黙って選ばない
- **必要なときは押し返す** — よりシンプルな方法があるなら、それを伝える
- **混乱したら止まる** — 何が不明なのかを言語化し、確認を求める

### 2. シンプルさを最優先する

**問題を解決する最小限のコード。推測による追加はしない。**

過剰設計の傾向に対抗します。

- 求められていない機能を追加しない
- 1回しか使わないコードのために抽象化しない
- 要求されていない「柔軟性」や「設定可能性」を追加しない
- 起こり得ないシナリオのためのエラーハンドリングを追加しない
- 200行を50行にできるなら、書き直す

**テスト:** シニアエンジニアが「これは複雑すぎる」と言うだろうか。そうなら、シンプルにする。

### 3. 外科的に変更する

**必要な箇所だけに触れる。自分が生んだ不要物だけを片付ける。**

既存コードを編集するとき:

- 隣接するコード、コメント、フォーマットを「改善」しない
- 壊れていないものをリファクタリングしない
- 自分なら別の書き方をする場合でも、既存のスタイルに合わせる
- 無関係な不要コードに気づいたら、削除せずに言及する

自分の変更によって孤立したものが生まれた場合:

- 自分の変更によって未使用になったimport、変数、関数を削除する
- 依頼されていない限り、既存の不要コードは削除しない

**テスト:** 変更されたすべての行が、ユーザーの依頼に直接結びついているべきです。

### 4. ゴール駆動で実行する

**成功条件を定義する。検証できるまでループする。**

命令型のタスクを、検証可能なゴールに変換します。

| 代わりに... | 次のように変換する... |
|-------------|-----------------------|
| 「バリデーションを追加して」 | 「不正な入力のテストを書き、それをパスさせる」 |
| 「バグを直して」 | 「バグを再現するテストを書き、それをパスさせる」 |
| 「Xをリファクタリングして」 | 「変更前後でテストが通ることを確認する」 |

複数ステップのタスクでは、短い計画を示します。

```
1. [ステップ] → 検証: [確認内容]
2. [ステップ] → 検証: [確認内容]
3. [ステップ] → 検証: [確認内容]
```

強い成功条件があれば、LLMは自律的にループできます。弱い条件（「動くようにして」）では、絶えず確認が必要になります。

## インストール

**Option A: Claude Codeプラグイン（推奨）**

Claude Code内で、まずマーケットプレイスを追加します。
```
/plugin marketplace add forrestchang/andrej-karpathy-skills
```

次にプラグインをインストールします。
```
/plugin install andrej-karpathy-skills@karpathy-skills
```

これにより、ガイドラインがClaude Codeプラグインとしてインストールされ、すべてのプロジェクトでスキルを利用できるようになります。

**Option B: CLAUDE.md（プロジェクトごと）**

新規プロジェクト:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md
```

既存プロジェクト（追記）:
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

## Cursorで使う

このリポジトリには、コミット済みのCursorプロジェクトルール（[`.cursor/rules/karpathy-guidelines.mdc`](.cursor/rules/karpathy-guidelines.mdc)）が含まれているため、Cursorでプロジェクトを開いたときにも同じガイドラインが適用されます。セットアップ、他のプロジェクトでのルール利用、Claude Codeとの関係については **[CURSOR.md](CURSOR.md)** を参照してください。

## 重要な洞察

Andrejより:

> 「LLMは、具体的なゴールを満たすまでループすることが非常に得意です。何をするかを指示するのではなく、成功条件を与えて、それが進むのを見守りましょう。」

「ゴール駆動で実行する」という原則は、この考え方を捉えています。命令型の指示を、検証ループを伴う宣言型のゴールへ変換します。

## うまく機能しているかを知る方法

次のような状態が見られれば、これらのガイドラインは機能しています。

- **diffに不要な変更が少ない** — 依頼された変更だけが現れる
- **過度な複雑化による書き直しが少ない** — 最初からコードがシンプルである
- **実装前に確認質問が来る** — ミスの後ではない
- **クリーンで最小限のPR** — ついでのリファクタリングや「改善」がない

## カスタマイズ

これらのガイドラインは、プロジェクト固有の指示と統合できるように設計されています。既存の `CLAUDE.md` に追加するか、新しく作成してください。

プロジェクト固有のルールには、次のようなセクションを追加します。

```markdown
## Project-Specific Guidelines

- Use TypeScript strict mode
- All API endpoints must have tests
- Follow the existing error handling patterns in `src/utils/errors.ts`
```

## トレードオフに関する注意

これらのガイドラインは、**速度よりも慎重さ** に寄せています。単純なタスク（簡単なタイポ修正、明らかな1行変更）では、状況に応じて判断してください。すべての変更に完全な厳密さが必要なわけではありません。

目的は、単純なタスクを遅くすることではなく、重要な作業で高くつくミスを減らすことです。
